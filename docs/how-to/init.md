# Инициализация проекта (`pegas init`)

> How-to: привязать Pegas к существующему проекту — контракт, скрипты, compose-хирургия.

Инициализирует проект и закладывает контракт оркестрации Pegas на этапе разработки.

```bash
# Инициализация текущего проекта
pegas init

# Безопасный предпросмотр без записи файлов
pegas init --dry-run

# Машиночитаемый JSON для AI-агентов
pegas init --json
```

---

## 1. Что делает `pegas init` в проекте

Выполняется разработчиком или AI-агентом в корне репозитория проекта:

1. **Создаёт декларативный контракт (`pegas.json`)**:
   - Автоматически вычисляет имя проекта (slug) из `package.json` или директории.
   - Инвентаризирует **все** сервисы `docker-compose.yml` (при наличии файла):
     - app-сервисы попадают в контракт целиком: `build` (`context`, `dockerfile`, `target`), `image`, `port`, `env`, `envFile`, `dependsOn` и домены каждого окружения;
     - infra-сервисы (базы данных, брокеры) — с `image`, named `volumes` и `role: "infra"`;
     - сервисы под `profiles` и собственные прокси (caddy/nginx) пропускаются: их активность не выводима из файла — это зона ручного решения;
     - значения с подстановками `${VAR}` не записываются как литералы;
     - канонический dev-алиас `<проект>.localhost` достаётся главному сервису (стандартное имя → порт → первый).
   - Харвестит структурные сигналы: порт из `EXPOSE` в `apps/<сервис>/Dockerfile` (для сервисов без порта в compose); каталоги `apps/*` без Dockerfile — кандидаты и в контракт не добавляются.
   - Харвестит домены из `Caddyfile` проекта (ищется в корне и в типовых директориях `caddy/`, `config/`, `docker/`, `deploy/`, `configs/`; корень приоритетнее): прод-домены блоков `домен { reverse_proxy <сервис>:<порт> }` копируются в контракт литералами вместо заглушек (www-redirect-блоки не копируются — шлюз строит их сам; сплит-роутинг и внешние сервисы пропускаются).
   - Прописывает dev-домены (`<сервис>.<проект>.localhost`); stage — единая заглушка `example.com` (стейдж-домен не выводим — только вручную); production — заглушка `<сервис>.example.com` (RFC 2606, маркер «не заполнено»), кроме случаев, когда реальный домен однозначно записан в Caddyfile проекта.
2. **Обвязывает `package.json`**:
   - Добавляет пакет `@netrunner714/pegas` в `devDependencies`.
   - Оборачивает скрипт `dev` в `pegas dev -- <команда>` (или создаёт `dev: "pegas dev"`).
   - Добавляет команду `deploy: "pegas deploy"`.
3. **Хирургия Docker Compose (`docker-compose.yml`)**:
   - Если файла нет — создаёт типовой compose-файл.
   - Если файл есть — трансформирует конфликтующие внешние порты (`ports: 3000:3000`) в `expose: 3000`.
   - Настраивает логирование (`json-file` с ротацией).
   - Подключает проект к внешней сети `pegas-network`.
4. **Создаёт документацию для ИИ-агентов (`docs/pegas.md`)**:
   - Правила контракта, адреса upstream и команды для Cursor, Claude Code, Cline.
5. **Защищает VCS (`.gitignore`)**:
   - Добавляет служебную директорию `.pegas` в `.gitignore`.

## 2. Безопасный предпросмотр (`--dry-run`)

Флаг `--dry-run` позволяет проверить, какие изменения будут внесены в проект, без физической записи на диск:

```bash
pegas init --dry-run
```

Выведет список запланированных действий:
```text
📋 [dry-run] Pegas project initialization preview:

  • Создан контракт pegas.json для проекта 'my-app'
  • Обновлён скрипт 'dev' в package.json: обёрнут в 'pegas dev --'
  • Добавлен скрипт 'deploy': 'pegas deploy' в package.json
  • Добавлен '@netrunner714/pegas' в devDependencies в package.json
  • Добавлена запись .pegas в .gitignore
  • Сгенерирован docs/pegas.md
  • Создан docker-compose.yml с expose и сетью pegas-network

No changes were written to disk. Run 'pegas init' to apply.
```

## 3. Тестирование совместимости на реальных репозиториях (`e2e:init`)

Для проверки того, как `pegas init` ведёт себя в дикой природе на настоящих (а не синтетических) проектах, реализован изолированный раннер совместимости:

```bash
# Проверка локального проекта (оригинал не модифицируется!)
bun run test:e2e:init /path/to/real-project

# Проверка удаленного репозитория с GitHub
bun run test:e2e:init https://github.com/user/repo --branch main

# С выводом визуального git diff изменений
bun run test:e2e:init /path/to/real-project --diff
```

### На что направлен `e2e:init`:
Тест **намеренно изолирован и сфокусирован только на самом первом шаге жизненного цикла** (еще до первой команды разработки `dev` и уж тем более до боевого `deploy`). Он не пытается запустить контейнеры или поднять шлюз, а проверяет самые базовые, но критичные вещи:

1. **Доступность пакета в NPM**: тянется ли пакет `@netrunner714/pegas` из глобального интернета через `npx` и стартует ли без ошибок окружения.
2. **Инструкции для ИИ-агентов (`docs/pegas.md`)**: создаётся ли документация архитектурных правил для Cursor, Claude Code, Cline и разработчиков.
3. **Декларативный контракт (`pegas.json`)**: генерируется ли валидный JSON-контракт, правильно ли определяются имя проекта, сервисы и порты.
4. **Обвязка `package.json`**:
   - Оборачивается ли существующий скрипт `dev` в `pegas dev -- <команда>`.
   - Добавляется ли скрипт `deploy: "pegas deploy"`.
   - Добавляется ли `@netrunner714/pegas` в `devDependencies`.
5. **Защита VCS (`.gitignore`)**: прописывается ли служебная папка `.pegas` в игнор Git.
6. **Хирургия Docker Compose**:
   - Был ли compose-файл вообще (или потребовалось создать с нуля).
   - Вырезались ли конфликтующие публичные веб-порты (80, 3000, 8080).
   - Сохранились ли порты инфраструктуры (Postgres 5432, Redis 6379).
   - Прописались ли директивы `expose`, проектные сетевые алиасы и внешняя сеть `pegas-network`.
7. **Валидность YAML для Docker Engine**: проверяет сгенерированный compose-файл через реальный `docker compose config --no-interpolate`, чтобы убедиться, что Docker принимает синтаксис (даже если боевые `.env` переменные отсутствуют).

### Изоляция и логи:
- **100% безопасность**: оригинальный репозиторий копируется в изолированную временную песочницу `/tmp/pegas-e2e-init-.../` без `node_modules` и кэшей. Оригинал никогда не меняется.
- **Полная диагностика**: детальный лог (stdout, stderr, пофайловый `git diff`, статус каждого шага) сохраняется в `.tmp/reports/e2e-init-<repo>-<timestamp>.log` для последующего анализа и поиска краевых кейсов.
