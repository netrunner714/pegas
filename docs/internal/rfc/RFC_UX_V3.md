# RFC: UX-путь Pegas v3

> **🔒 Внутренний документ pegas.** Не является пользовательской документацией.
> **Статус: реализовано в pegas 3.0.0** — план выполнен, перенесён сюда как историческая запись.
> Актуальное поведение описывает публичная документация: README.md, docs/reference/contract.md, llms.txt.

> **Статус:** Обсуждение (Draft)
> **Дата:** 4 ноября 2026 г.
> **Связанные документы:** [`RFC_CONTRACT_V3.md`](./RFC_CONTRACT_V3.md) — спецификация контракта, [`example.json`](./example.json) — эталонный контракт.

---

## 1. Принцип разделения записи

Весь UX-путь строится на одной границе:

| Территория | Кто пишет | Когда |
|---|---|---|
| Файлы проекта (`package.json`, `pegas.json`, `.gitignore`, `AGENTS.md`, `docs/pegas.md`) | pegas — только `init` (один раз); далее — LLM/пользователь | шаг 1, 3, 4 |
| Рантайм машины (`~/.pegas`, маршруты шлюза, сертификаты, контейнеры) | pegas | шаги 2, 5, 6 |

Pegas не создаёт `.env`, `.env.example`, Dockerfile, не харвестит существующий код и не мутирует чужие файлы после `init`. «Умного» чтения репозитория нет ни в одном пути: переход v2→v3 — ручная правка контракта по подсказкам `pegas check`, в контексте самого репо.

## 2. Путь пользователя: команды

| # | Команда | Частота | Что делает |
|---|---|---|---|
| 1 | `bun add -d @netrunner714/pegas` | 1 раз на репо | Добавляет devDependency. Никакой код pegas при этом не выполняется |
| 2 | `pegas ca install` | 1 раз на машину | Устанавливает доверенный локальный Root CA для dev-HTTPS |
| 3 | `pegas init` | 1 раз на проект | «Первое касание» — создаёт артефакты интеграции (см. §3) |
| 4 | *(ручной шаг)* — написание `pegas.json` | 1 раз + правки | Контракт пишет LLM/пользователь по схеме и эталону (см. §4) |
| 5 | `pegas connect` | 1 раз перед каждой dev-сессией | Подключает маршруты проекта к шлюзу (`*.localhost` → хост) |
| 6 | `pegas deploy -s development` + `bun run dev` | каждый dev-день | Деплой поднимает только docker-сервисы; host-приложения пользователь запускает сам (см. §6) |

Продакшенная ветка пути (после заполнения доменов и секретов): `pegas deploy -s production`, `pegas logs -f`, `pegas status`, `pegas check`, `pegas down`, `pegas disconnect` — без изменений относительно v2, кроме адаптации к v3-контракту.

## 3. `pegas init` — первое касание (1 раз на проект)

Тонкий детерминированный scaffolder. Никакого анализа репозитория, никакой сети, никакого чтения compose/Caddyfile. Только создаёт:

- **Блок в `AGENTS.md`** — маркер-блок `<!-- BEGIN:pegas-rules --> ... <!-- END:pegas-rules -->` с правилами контракта для ИИ-агентов (канонический текст, единый для всех репо).
- **`docs/pegas.md`** — документация проекта про pegas: команды, правила контракта, паттерн расширения при добавлении сервисов.
- **`.pegas/`** — каталог рантайма проекта (гитигнорится).
- **Записи в `.gitignore`** — `.pegas`, `.env` (только дополнение отсутствующих строк).

Свойства:
- идемпотентен: повторный запуск ничего не перезатирает; маркер-блок обновляется только при смене версии канона;
- не трогает существующий `pegas.json` (даже невалидный — его чинит `check`);
- `--dry-run` — предпросмотр.

Выход из pegas — без команды: инструкция в docs/how-to (удалить маркер-блок, `docs/pegas.md`, `pegas.json`, `.pegas/`, записи `.gitignore`, `bun remove`, `down`/`disconnect` при подключённом рантайме).

Что удалено относительно v2: `uninstall` (целиком, вместе с обёрткой dev-скриптов), харвесты, генерация `.env`/`.env.example`, starter-Dockerfile, compose-хирургия, проверки версий npm, предзагрузка Caddy, reconcile контракта.

## 4. `pegas.json` — ручное (LLM) авторство

Контракт не генерируется тулингом — его пишет агент или человек. Поддержка авторства держится на трёх опорах:

1. **`$schema`** в IDE — подсказки полей и типов прямо при редактировании; схема — единственный корень правды о контракте.
2. **Эталон — генерируемый артефакт схемы.** Файла `example.json`, который правится руками, не существует. Вместо этого:
   - `schemas/pegas.json` — единственный источник: описания полей, enum'ы, значения-примеры (`examples`/`default`) живут в самой схеме;
   - `scripts/gen-example.ts`: schema → эталон; пересборка в CI, ручные правки запрещены;
   - **npm**: эталон и схема публикуются в пакете (`files`), агент читает их из `node_modules`;
   - **облако**: сайт уже хостит `/schemas/pegas.json` — рядом добавляются эталон и reference-страница «поле за полем» (генерируется из описаний той же схемы);
   - эталон **не кладётся в клиентские репо**: агент считывает его в момент написания контракта (пакет/облако), не сохраняет копию — копия в репо означала бы второй источник правды с гарантированным drift;
   - `scripts/gen-llms.ts` / `gen-docs.ts` включают эталон (или ссылку на него) в свои выходы.
3. **`pegas check`** — рид-онли валидатор: полнота матрицы сценариев, паритет `services.*.secrets` ↔ `.env` (если существует), `domains` только у HTTP-сервисов, `ports: []` вне dev и т.д. Ошибки — машиночитаемые (`--json`), с подсказкой «что дописать».

Инвариант: schema → { example, llms.txt, docs, сайт } — все производные генерируются из одного корня; `docs:check` и CI-тест «эталон валиден по схеме» следят за отсутствием рассинхрона.

## 5. `pegas connect` / `pegas disconnect`

Решение: `link`/`unlink` переименовываются в `connect`/`disconnect` — без алиасов, старые имена удаляются (breaking-изменение в составе major 3.0). Семантика без изменений:

- `connect` — регистрирует dev-маршруты проекта в общем шлюзе: `[service].[project].localhost` → `host.docker.internal:<port>`; предзагрузка Caddy и CA-хинт живут здесь (а не в init);
- `disconnect` — освобождает dev-маршруты;
- вызывается 1 раз перед началом каждой dev-сессии; между сессиями маршруты можно держать подключёнными.

## 6. `pegas dev` — отклонено (свободный темп + докер-семантика deploy)

Супервизор host-процессов не делаем. Dev-цикл в v3:

```bash
pegas connect                 # маршруты проекта в Caddy (правила установлены)
pegas deploy -s development   # только docker-сервисы сценария: контейнеры + readiness
bun run dev                   # host-сервисы — когда захочет пользователь
```

Ключевое правило: **`pegas deploy -s <scenario>` всегда поднимает только сервисы с `driver: "docker"`** — в любом сценарии, не только в development. Host-драйвер (`driver: "bun"`) означает «этот сервис в данном сценарии pegas не касается»: его запуск, логи и жизненный цикл — территория пользователя (`package.json`, `bun run <script>`).

Отсюда же следует чистка контракта: поля `up` нет — команда запуска host-сервиса дублировала бы `package.json` scripts (pegas их не мутирует и не может держать синхронными). Контракт не обещает того, что не исполняет. Подробности — столп 3 в `RFC_CONTRACT_V3.md`.

Решение окончательное, без «докатим в 3.1»: конвенции запуска (`apps/<service>`, override) не проектируются — без исполнителя им нечего исполнять.

## 7. Реестр решений и открытых вопросов

| # | Вопрос | Статус |
|---|---|---|
| 1 | `init` остаётся как «первое касание» (тонкий scaffolder, 1 раз на проект) | ✅ принято |
| 2 | Харвесты и «умный» init вырезаны полностью; команды `migrate` нет — переход v2→v3 это ручная правка pegas.json по подсказкам `pegas check` (агентом или владельцем, в контексте самого репо) | ✅ принято |
| 3 | Pegas не пишет `.env`/`.env.example`/Dockerfile — территория LLM/пользователя | ✅ принято |
| 4 | `check` — рид-онли валидатор (без `--fix`) | ✅ принято |
| 5 | Эталон контракта — генерируемый артефакт JSON Schema: schema → example → llms/docs/site/npm, один корень | ✅ принято |
| 6 | Rename `link`/`unlink` → `connect`/`disconnect` без алиасов (breaking, в составе major 3.0) | ✅ принято |
| 7 | `pegas dev` — отклонён: супервизора нет; `deploy -s` всегда поднимает только docker-сервисы, host-сервисы запускает пользователь | ✅ принято |
| 8 | `uninstall` удаляется: команда не создаётся, выход из pegas — ручной по инструкции из документации | ✅ принято |
| 9 | `npx`-вход и делегация в `node_modules` умирают (все команды через локальный bin) | ✅ принято |
