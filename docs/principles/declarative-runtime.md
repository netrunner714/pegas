# RFC: декларативный рантайм Pegas (Pegas 2.0)

> Статус: **архитектура согласована, решения Q1–Q5 зафиксированы** (обсуждение 2026-10-31).
> Не является реализацией. Документ фиксирует архитектурные решения до написания кода.
> Ссылки: [artifacts.md](./artifacts.md) — закон файловых артефактов, который этот RFC обязан соблюсти.

---

## 1. Цель одним абзацем

Pegas перестаёт быть обёрткой над dev-процессом и становится **декларативным менеджером окружений**: пользователь описывает желаемое окружение в `pegas.json`, а Pegas сам создаёт контейнеры, сети, роуты и управляет их жизненным циклом. Development и production используют одну контейнерную и сетевую модель, различаясь режимом приложения и политиками эксплуатации. Жизненный цикл окружения не привязан к CLI-сессии: контейнеры живут между терминалами, Pegas подключается к уже работающим.

## 2. Решения, зафиксированные этим RFC

| # | Решение | Обоснование |
|---|---|---|
| D1 | `pegas.json` — единственный источник истины; Compose — только механизм реализации | Продолжение текущей позиции: контракт уже описывает сервисы/домены, compose уже генерируется из него |
| D2 | Инфраструктура (postgres, redis и т. д.) **попадает в контракт** — осознанный сдвиг границы суверенитета | Прямое исполнение раздела 3 [artifacts.md](./artifacts.md): решение принимается явно, не «пофакту реализации» |
| D3 | Генерируемый манифест запуска — **эфемерный артефакт**: живёт в памяти команды или во временном файле, удаляется после применения | Устраняет нарушителя № 4 из инвентаризации [artifacts.md](./artifacts.md#4-инвентаризация-сейчас--хотим); Compose-файлы больше не оседают в `.pegas/` |
| D4 | Оркестрация через `docker compose -f <манифест>` (stdin/temp), а не ручные `docker run` | Меньше кода, battle-tested зависимости, отлаживаемость |
| D5 | Идентификация контейнеров и reconciliation — через Docker labels (`pegas.project`, `pegas.service`, `pegas.manifest-hash`) | Statelessness: состояние читается из Docker, state-файлов нет |
| D6 | Gateway — shared-ресурс машины; остановка по факту «подключённых проектов не осталось» (refcount через inspect сети) | Жизненный цикл не привязан к CLI |
| D7 | Новая модель — **opt-in** (`runtime: "docker"` в `pegas.json`), старый флоу остаётся default | SemVer major для смены семантики `pegas dev`; смена default — не раньше 2.0 |
| D8 | Dev-приложения: типовой образ по стеку по умолчанию (Node/Bun/Python), override через контракт; нераспознанный стек без override — явная ошибка | Q1: zero-config для стандартных проектов без угадывания нестандартных |
| D9 | Занятость 80/443 на dev-машине — fail fast, без автоматического fallback на 8080/8443 | Q2: тихий fallback ломает обещание доменов без порта |
| D10 | `node_modules` в named volume; установка внутри контейнера только при изменении lock-файла; volume не пересоздаётся | Q3: экономия времени и предсказуемость |
| D11 | HMR — платформенно-зависимая модель: Linux — файловые события; macOS/Windows — polling только при необходимости; «dev успешен» требует работающего file-watching | Q4: главный UX-критерий |
| D12 | Обновление production — целевая модель (новый контейнер → readiness → переключение роута → остановка старого); реализация вне S1; zero-downtime для одного экземпляра не гарантируется | Q5: честные обязательства |

## 3. Контракт `pegas.json` v2 (расширение схемы)

Все новые поля optional — старые контракты валидны и работают как раньше (SemVer minor на этапе opt-in).

```jsonc
{
  "projectName": "<проект>",
  "runtime": "docker",              // D7: opt-in. отсутствует/"host" = текущее поведение
  "services": {
    "<сервис>": {
      // существующее (не меняется)
      "port": <порт>,
      "upstream": "<сервис>:<порт>",
      "domains": { "development": ["<домен>"], "production": ["<домен>"] },

      // новое: приложение
      "build": { "context": "<путь>", "dockerfile": "<путь>" },  // или
      "image": "<образ>",
      "command": ["<команда dev-сервера>"],          // напр. ["npm", "run", "dev"]
      "env": { "<КЛЮЧ>": "<значение>" },
      "volumes": ["<имя-тома>:<путь-в-контейнере>"], // node_modules и т. п.
      "bindMount": "<путь-к-исходникам>",            // по умолчанию "." проекта

      // новое: инфраструктура (D2)
      "role": "app" | "infra"
    }
  }
}
```

Правила:

- Сервис без `build`/`image` и с известным инфраструктурным профилем (postgres/redis/…) Pegas предлагает как инфраструктуру с готовым образом — но подтверждает у пользователя при `pegas init`.
- `node_modules` в именованный том Pegas подключает автоматически для app-сервисов; синхронизация при изменении lock-файла — ответственность рантайма (см. решение Q3, D10).
- Для app-сервиса без `image`/`build` применяется типовой dev-образ по детекции стека (D8); стек не распознан и override не задан — ошибка.
- `hmr`: платформенно-зависимое поведение по умолчанию, override через контракт (D11): `"hmr": { "fileWatch": "auto" | "events" | "polling" }`.

## 4. Модель запуска

- Общая сеть `pegas-network` (external) — уже существует, переиспользуется.
- Общий Caddy Gateway — один контейнер на машину, обслуживает все проекты по DNS-алиасам сервисов (`<проект>-<сервис>:<порт>` внутри сети).
- Dev-приложения: контейнер + bind mount исходников + команда дев-сервера + изолированный том зависимостей. Несколько проектов могут слушать одинаковый порт — сетевые namespace разные.
- Манифест подъёма (compose-формат) генерируется из контракта, применяется через `docker compose -f -` (stdin) или временный файл, **и удаляется** — D3.
- Идемпотентность: hash манифеста пишется в labels. `pegas dev`: hash совпал и контейнеры живы → ничего не пересоздаём, сразу подключаемся к логам.

## 5. Семантика команд (новая, при `runtime: "docker"`)

| Команда | Ответственность |
|---|---|
| `pegas init` | Подготовка проекта и создание контракта (как сейчас) |
| `pegas deploy development` | Развёртывание dev-окружения: сеть, gateway, контейнеры, роуты |
| `pegas dev` | Проверка соответствия контракту и подключение к логам; Ctrl+C отваливает логи, не останавливая контейнеры |
| `pegas deploy production` | Развёртывание production-окружения (та же модель) |
| `pegas down` | Остановка ресурсов проекта; gateway останавливается, когда подключённых проектов не осталось |

Сборка: infra-сервисы с готовыми образами — без `--build`; dev-приложения собираются при изменении `build`-полей контракта; исходники не требуют пересборки.

## 6. Миграция и SemVer

| Стадия | Содержание | Версия |
|---|---|---|
| S1 | Расширение контракта + codegen манифеста (эфемерный) + labels; opt-in `runtime: "docker"`; `pegas deploy development` | minor |
| S2 | Shared gateway в dev, CA-доверие для контейнера gateway | minor |
| S3 | Новый `pegas dev` = проверка + attach к логам | minor (внутри opt-in) |
| S4 | `pegas down` с refcount-остановкой gateway | minor |
| S5 | Смена default → новая модель; deprecated-период старого флоу | **major (2.0)** |

Старый host-флоу (`pegas dev` с локальным Caddy) поддерживается до 2.0 включительно. Инструмент миграции контракта — часть S5.

## 7. Согласованные решения (Q1–Q5, обсуждение 2026-10-31)

### Q1. Dockerfile для dev-приложений — гибридная модель

Принято: Pegas сам обеспечивает типовые dev-образы для распространённых стеков:

- Node.js / Next.js — типовой Node-образ; Bun — типовой Bun-образ; Python — типовой Python-образ.
- Pegas определяет стек, версию runtime и пакетный менеджер по проекту (`package.json`, lock-файл).
- Пользователь может переопределить образ или Dockerfile через `pegas.json` (`image` / `build`).

Принцип: **стандартный проект не требует написания Dockerfile ради работы в Pegas.**

Ограничение: Pegas не пытается угадать любую конфигурацию. Нестандартный проект — пользователь явно описывает параметры в контракте. Если стек не распознан и override не задан — явная ошибка с диагностикой, не тихий fallback на «что-нибудь похожее».

### Q2. Занятые порты 80/443 — fail fast

Принято: никакого автоматического переноса Gateway на 8080/8443 — это ломает обещание локальных доменов без указания порта.

При конфликте Pegas:

- сообщает, какой порт занят (и кем — по возможности);
- показывает вероятную причину;
- не запускает неполноценное окружение и не меняет адреса проекта.

Альтернативные порты в будущем — только через явную конфигурацию в контракте, отдельным режимом, не автоматическим fallback.

### Q3. Синхронизация `node_modules` — named volume + синхронизация по lock-файлу

Модель:

```
Project
  ├── source files → bind mount
  ├── package.json → bind mount
  ├── lock file     → bind mount
  └── node_modules  → named volume
```

- При `deploy development` Pegas проверяет lock-файл (хэш сохраняется в контейнере/volume).
- Изменился — установка зависимостей **внутри контейнера** в существующий volume; не менялся — установка не выполняется.
- Volume **не пересоздаётся** при каждом изменении: сохраняется и синхронизируется по содержимому.

Хост: пользователь ставит зависимости привычным способом (`package.json` + lock-файл через git). Поведение при `npm install` прямо на хосте (появление хостового `node_modules` под bind mount) — см. открытый вопрос Q6.

### Q4. Hot Reload — платформенно-зависимая модель

- Linux: стандартные файловые события (эталон).
- macOS / Windows: штатная синхронизация Docker; polling (CHOKIDAR_USEPOLLING и аналоги) — только там, где требуется, не глобально.
- Поведение переопределяется через `pegas.json`.
- HMR проверяется тестами на поддерживаемых стеках.

Критерий успеха: **Pegas не считает контейнерный dev успешным, если приложение запускается, но изменения файлов не обнаруживаются.** Это главный UX-критерий новой модели.

### Q5. Обновление production-деплоев — целевая модель зафиксирована, реализация вне S1

Целевой механизм обновления (реализация — отдельный этап после S1–S4):

1. Собрать новый образ.
2. Запустить новый контейнер.
3. Дождаться успешной проверки готовности.
4. Переключить маршрутизацию на новую версию.
5. Остановить старый контейнер.

Для одного экземпляра приложения без возможности параллельного запуска полноценный zero-downtime deploy **не гарантируется** — это фиксируется в документации честно.

## 8. Критерии готовности S1

Код S1 не начинается, пока не выполнены все пункты:

1. **Контракт v2 спроектирован и покрыт тестами схемы** (все новые поля optional, старые контракты валидны).
2. **Codegen манифеста** эфемерен: генерация → применение → удаление; временный файл не переживает команду (закрытие нарушителя № 4 artifacts.md).
3. **Детекция стека** (Node/Bun/Python, версия runtime, пакетный менеджер) реализована и тестируется на репрезентативных проектах.
4. **Labels** (`pegas.project`, `pegas.service`, `pegas.manifest-hash`) записываются при подъёме и читаются при reconciliation.
5. **Q2 реализован**: занятость 80/443 проверяется до подъёма gateway, диагностика называет порт и процесс-виновник.
6. **Q3 реализована в базовом виде**: хэш lock-файла сравнивается, установка в контейнере выполняется только при изменении, volume сохраняется.
7. Тесты не зависят от платформы запуска (Linux CI достаточно; платформенные ветки — unit-мок).
8. `pegas.json` без `runtime: "docker"` не меняет поведение ни одной существующей команды.

## 9. Открытые вопросы, выявленные при уточнении (не блокируют S1, требуют решения до S3)

- **Q6. Хостовая установка зависимостей.** `npm install` на хосте создаёт `node_modules` в директории проекта — она под bind mount перекроет (или будет перекрыта) томом контейнера. Нужно определить: запрещаем ли, предупреждаем ли, или документируем «так делать не нужно». Предложение: предупреждение в `pegas dev`/`deploy` + документация.
- **Q7. Порядок стадий для миграции живых серверов.** Q5 зафиксировал целевую модель обновления, но порядок внедрения эфемерных манифестов на уже работающих серверах (без остановки) — отдельный план до S5.
- **Q8. Обновление типовых dev-образов.** Кто и когда поднимает версии базовых образов (Node LTS → следующий LTS)? Предложение: `pegas update` расширяется на проверку актуальности типовых образов.
- **Q9. Привилегии на запись в named volume при первом запуске.** Установка внутри контейнера может потребовать прав на запись в volume от пользователя контейнера (root по умолчанию — ок; не-root образы Python/Node — проверить uid/gid).
