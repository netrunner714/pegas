# RFC: декларативный рантайм Pegas (Pegas 2.0)

> Статус: **архитектура согласована, решения Q1–Q5 зафиксированы** (обсуждение 2026-10-31).
> Не является реализацией. Документ фиксирует архитектурные решения до написания кода.
> Ссылки: [artifacts.md](./artifacts.md) — закон файловых артефактов, который этот RFC обязан соблюсти.

---

## 1. Цель одним абзацем

Pegas перестаёт быть обёрткой над dev-процессом и становится **декларативным менеджером окружений**: пользователь описывает желаемое окружение в `pegas.json`, а Pegas сам создаёт контейнеры, сети, роуты и управляет их жизненным циклом. Development и production используют одну контейнерную и сетевую модель, различаясь режимом приложения и политиками эксплуатации. Жизненный цикл окружения не привязан к CLI-сессии: контейнеры живут между терминалами, Pegas подключается к уже работающим.

## 2. Решения, зафиксированные этим RFC

| # | Решение | Обоснование |
|---|---|---|
| D1 | `pegas.json` — единственный источник истины; Compose — только механизм реализации | Продолжение текущей позиции: контракт уже описывает сервисы/домены, compose уже генерируется из него |
| D2 | Инфраструктура (postgres, redis и т. д.) **попадает в контракт** — осознанный сдвиг границы суверенитета | Прямое исполнение раздела 3 [artifacts.md](./artifacts.md): решение принимается явно, не «пофакту реализации» |
| D3 | Генерируемый манифест запуска — **эфемерный артефакт**: живёт в памяти команды или во временном файле, удаляется после применения | Устраняет нарушителя № 4 из инвентаризации [artifacts.md](./artifacts.md#4-инвентаризация-сейчас--хотим); Compose-файлы больше не оседают в `.pegas/` |
| D4 | Оркестрация через `docker compose -f <манифест>` (stdin/temp), а не ручные `docker run` | Меньше кода, battle-tested зависимости, отлаживаемость |
| D5 | Идентификация контейнеров и reconciliation — через Docker labels (`pegas.project`, `pegas.service`, `pegas.manifest-hash`) | Statelessness: состояние читается из Docker, state-файлов нет |
| D6 | Gateway — shared-ресурс машины; остановка, когда контейнеров **других** проектов не осталось. Источник зависимостей — `docker ps -a` с фильтром по `pegas.project` (включая остановленные), а не endpoints сети. Остановленный контейнер **сохраняет** зависимость; освобождает её только удаление контейнера (`pegas down` / ручной `docker rm`) | Жизненный цикл не привязан к CLI; registry надёжен для остановленных проектов |
| D7 | Новая модель — **opt-in** (`runtime: "docker"` в `pegas.json`), старый флоу остаётся default | SemVer major для смены семантики `pegas dev`; смена default — не раньше 2.0 |
| D8 | Dev-приложения: типовой образ по стеку по умолчанию (Node/Bun/Python), override через контракт; нераспознанный стек без override — явная ошибка | Q1: zero-config для стандартных проектов без угадывания нестандартных |
| D9 | Занятость 80/443 на dev-машине — fail fast, без автоматического fallback на 8080/8443 | Q2: тихий fallback ломает обещание доменов без порта |
| D10 | `node_modules` в named volume; установка внутри контейнера только при изменении lock-файла; volume не пересоздаётся | Q3: экономия времени и предсказуемость |
| D11 | HMR — платформенно-зависимая модель: Linux — файловые события; macOS/Windows — polling только при необходимости; «dev успешен» требует работающего file-watching | Q4: главный UX-критерий |
| D12 | Обновление production — целевая модель (новый контейнер → readiness → переключение роута → остановка старого); реализация вне S1; zero-downtime для одного экземпляра не гарантируется | Q5: честные обязательства |
| D13 | Эфемерный манифест: создаётся в безопасном временном каталоге (`os.tmpdir()`/`pegas-<pid>-<рандом>`), удаляется при штатном завершении; оставшиеся после аварии временные файлы вычищаются при следующем запуске; секреты в манифест не попадают (env_file по ссылке, см. 4.3), временный файл — mode 0600 | Аварийное завершение Pegas между генерацией и удалением не должно оставлять следов и утечек |
| D14 | `manifest-hash` — хэш **эффективной конфигурации** (нормализованного манифеста, см. 4.2): без нестабильных значений (временные метки) и секретов; абсолютный путь проекта не входит. Drift = несовпадение хэша в labels с текущим контрактом (по каждому сервису отдельно); несовпадение — `pegas deploy` пересоздаёт, `pegas dev` **только сообщает**, не выполняет разрушительных изменений | Reconciliation предсказуем: исправление — явная команда, диагностика — тихая |
| D15 | Ключ синхронизации зависимостей = хэш lock-файла + пакетный менеджер + его версия + версия runtime | Одинаковый lock-файл при разных Node/npm даёт разное `node_modules` |
| D16 | Ошибка Docker bind при занятом порту преобразуется в диагностику Pegas (порт, вероятный виновник) — предварительная проверка 80/443 не снимает race condition между проверкой и bind | Q2: понятная ошибка в любом сценарии конфликта |
| D17 | Типовой dev-контейнер запускается от числового UID/GID пользователя-хозяина на POSIX; если Pegas запущен через sudo, используются SUDO_UID/SUDO_GID, иначе при недоступных значениях — непривилегированный fallback 1000:1000. Каталог workspace и путь dependency volume создаются и получают эти права на этапе сборки образа до bind mount; процесс запускается с тем же UID/GID, HOME указывает на доступный каталог | Запись в named volume и совместимость с правами исходников без запуска приложения от root |
| D18 | Жизнеспособность владельца временного каталога проверяется живым процессом (PID + имя процесса/время его старта, устойчивое к повторному использованию PID), а не возрастом файла. Каверзные случаи: длительный Pegas-процесс со старым каталогом — не мусор; аварийно завершённый процесс — каталог вычищается | Очистка после аварии не должна задевать живые параллельные процессы |
| D19 | Секреты: `envFile` в контракте (ссылка на gitignored файл), содержимое передаётся через Docker `env_file`, в манифест/labels/логи не попадает. Для обнаружения изменений используется `pegas.env-hash` — операционный fingerprint содержимого, а не средство защиты секрета: обычный хэш может допускать offline-проверку низкоэнтропийных значений. Пересоздание — только через `pegas deploy` | D13/D14 предполагали ссылочную передачу без определённого контракта — пробел закрыт; security-свойства fingerprint явно ограничены |
| D20 | Конкурентные операции, затрагивающие общий Gateway, сериализуются одной межпроцессной блокировкой в системном temp-каталоге. Блокировка атомарно захватывается созданием lock-directory; содержит PID, идентификатор процесса/время старта и heartbeat. Владелец удерживает её на всём критическом участке deploy/down. После аварии lock признаётся устаревшей только при доказанном завершении владельца; если это нельзя надёжно установить, операция завершается безопасной ошибкой, не удаляя lock. Ожидание ограничено таймаутом с понятной диагностикой. Постоянный registry не вводится | Проверка «сразу перед stop» не атомарна; intent-файлы не обеспечивают взаимного исключения и допускают race |

> Решения D17–D20 добавлены по итогам уточнения runtime lifecycle и ревью полного текста RFC.

## 3. Контракт `pegas.json` v2 (расширение схемы)

Все новые поля optional — старые контракты валидны и работают как раньше (SemVer minor на этапе opt-in).

```jsonc
{
  "projectName": "<проект>",
  "runtime": "docker",              // D7: opt-in. отсутствует/"host" = текущее поведение
  "services": {
    "<сервис>": {
      // существующее (не меняется)
      "port": <порт>,
      "upstream": "<сервис>:<порт>",
      "domains": { "development": ["<домен>"], "production": ["<домен>"] },

      // новое: приложение
      "build": { "context": "<путь>", "dockerfile": "<путь>" },  // или
      "image": "<образ>",
      "command": ["<команда dev-сервера>"],          // напр. ["npm", "run", "dev"]
      "env": { "<КЛЮЧ>": "<значение>" },             // несекретные переменные
      "envFile": "<путь-к-gitignored-env-файлу>",    // секреты — по ссылке (см. 4.3)
      "volumes": ["<имя-тома>:<путь-в-контейнере>"], // node_modules и т. п.
      "bindMount": "<путь-к-исходникам>",            // по умолчанию "." проекта

      // новое: инфраструктура (D2)
      "role": "app" | "infra"
    }
  }
}
```

Правила:

- Сервис без `build`/`image` и с известным инфраструктурным профилем (postgres/redis/…) Pegas предлагает как инфраструктуру с готовым образом — но подтверждает у пользователя при `pegas init`.
- `node_modules` в именованный том Pegas подключает автоматически для app-сервисов; синхронизация при изменении lock-файла — ответственность рантайма (см. решение Q3, D10).
- Для app-сервиса без `image`/`build` применяется типовой dev-образ по детекции стека (D8); стек не распознан и override не задан — ошибка.
- `hmr`: платформенно-зависимое поведение по умолчанию, override через контракт (D11): `"hmr": { "fileWatch": "auto" | "events" | "polling" }`.

## 4. Модель запуска

- Общая сеть `pegas-network` (external) — уже существует, переиспользуется.
- Общий Caddy Gateway — один контейнер на машину. Каждый checkout и environment (`development`, `stage`, `production`) получает отдельное имя Compose-проекта; контейнеры помечаются `pegas.project` и `pegas.environment`. DNS-алиас сервиса внутри общей сети имеет вид `<checkout-id>-<environment>-<сервис>:<порт>`, поэтому dev/stage/prod одного checkout не конкурируют за один alias.
- Dev-приложения: контейнер + bind mount исходников + команда дев-сервера + изолированный том зависимостей. Несколько проектов могут слушать одинаковый порт — сетевые namespace разные.
- Манифест подъёма (compose-формат) генерируется из контракта, применяется через `docker compose -f -` (stdin) или временный файл, **и удаляется** — D3.
- Идемпотентность: hash манифеста пишется в labels. `pegas dev`: hash совпал и контейнеры живы → ничего не пересоздаём, сразу подключаемся к логам.
- Единая нормализация имён окружений (`dev`/`development`, `prod`/`production`) действует во всех частях системы: labels `pegas.environment`, имя Compose-стека, DNS-алиасы, upstream Caddy и имя route-файла Gateway. Aliase-имена окружений не создают параллельных артефактов: при `deploy` канонического имени устаревшие route-файлы этого же checkout, оставшиеся от alias-имён, удаляются.
- Имена томов зависимостей включают окружение (`pegas-<checkout-id>-<сервис>-<environment>-dependencies`): dev и production одного checkout не делят `node_modules`.
- В development исходники приходят через bind mount и **не участвуют** в fingerprint образа: правка исходника не пересобирает образ. Fingerprint образа составляют Dockerfile, `.dockerignore` и (для не-development окружений) содержимое build context.
- `pegas down --env <environment>` удаляет контейнеры и route-файлы только указанного окружения; без `--env` — все окружения checkout. В обоих случаях остановка Gateway происходит по общим правилам D6.
- `pegas dev` подключается к логам через `logs --follow`; Ctrl+C (SIGINT) пробрасывается в Compose и отваливает только просмотр — контейнеры продолжают работать.

### 4.1. Регистрация зависимостей и освобождение Gateway (lifecycle-модель)

Учёт «кому ещё нужен Gateway» держится на контейнерах проекта, читаемых **из Docker целиком, а не из endpoints сети**:

- Каждый контейнер проекта запускается с labels `pegas.project`, `pegas.service`, `pegas.manifest-hash` и подключён к `pegas-network`.
- **Источник зависимостей** — `docker ps -a --filter label=pegas.project` (все контейнеры, включая остановленные). `docker network inspect` для учёта зависимостей **не используется**: он показывает только подключённые endpoints и «теряет» остановленный контейнер.
- **Семантика остановленного контейнера**: `docker stop` **не освобождает** зависимость — остановленный проект продолжает числиться держателем. Зависимость освобождается только удалением контейнера: `pegas down` удаляет контейнеры проекта, либо ручной `docker rm`. Обоснование: `pegas down` ≠ пауза; повторный `pegas dev`/`deploy` поднимает те же контейнеры, и Gateway должен быть доступен (контейнеры пересоздаются, если их нет).
- **Идентичность Gateway** — отдельный машинный ресурс с label `pegas.gateway = true`; он не принадлежит первому проекту и не наследует его lifecycle. Зависимость проектов определяется только labels их собственных контейнеров.
- `pegas down` проекта: удаляет свои контейнеры → затем `docker ps -a` с фильтром по `pegas.project` → если контейнеров с **другими** проектами не осталось → останавливает Gateway. Сеть остаётся (external, дешёвая).
- **Координация конкурентных операций**: `deploy` и `down` захватывают одну и ту же эксклюзивную межпроцессную блокировку до любых изменений общего Gateway и удерживают её до завершения всей критической секции. Внутри блокировки `deploy` обеспечивает сеть/Gateway, создаёт или обновляет контейнеры и маршруты; `down` удаляет контейнеры и маршруты проекта, повторно проверяет registry через `docker ps -a` и останавливает Gateway только при отсутствии держателей. Блокировка реализуется атомарным созданием lock-directory в системном temp-каталоге; владелец записывает PID, устойчивый идентификатор процесса/время старта и обновляет heartbeat. Параллельная команда ждёт освобождения до заданного таймаута. После аварии lock можно перехватить только если завершение владельца доказано; при неопределённости Pegas отказывается от операции и не удаляет lock. Блокировка эфемерна, не является registry и удаляется после штатной операции; держатели по-прежнему определяются только Docker labels.
- **Авария или ручное удаление контейнеров**: `docker rm` снимает зависимость; `docker stop` — нет (см. выше). Если контейнеры проекта удалены, а Gateway жив — Gateway обслуживает остальных; остановится при следующем `pegas down` любого проекта либо остаётся до ручной остановки.
- **Авария самого Gateway**: контейнеры проектов продолжают работать (Gateway не участвует в их жизненном цикле). Следующий `pegas deploy`/`pegas dev` любого проекта обнаруживает отсутствие Gateway и поднимает его заново (проверка `getGatewayContainerStatus` — механизм уже есть). Постоянный state-файл не нужен: состояние «Gateway поднят» читается из Docker.
- **Восстановление после частичной аварии** (контейнеры проекта живы, Gateway удалён вручную): роуты проекта недоступны до ближайшего `pegas deploy`/`dev` — документированное поведение; Gateway поднимается заново с теми же роутами, контейнеры не пересоздаются.

### 4.2. Состав `manifest-hash` (уточнение D14)

- **Вход**: эффективная конфигурация сервиса после разрешения всех defaults и детекции стека — итоговый манифест в нормализованном виде (сортировка ключей, стабильная сериализация).
- **Исключаются**: секреты (см. 4.3), нестабильные значения (пути временных файлов, порты авто-подбора — в Docker-модели их нет, но правило фиксируется), абсолютный путь проекта на хосте (хэш должен совпадать на разных машинах — иначе один и тот же контракт даст drift).
- **Частичный drift**: контейнеры разных сервисов одного проекта могут иметь разные хэши (пересоздавались по отдельности). `pegas dev`/`deploy` сравнивает хэш **по каждому сервису отдельно**, а не один общий; сообщение о drift перечисляет конкретные сервисы.
- Пересоздание при drift — всегда через `pegas deploy` (D14): `dev` только сообщает.

### 4.3. Секреты: передача и семантика изменения

- **Контракт передачи**: в `pegas.json` поле `env` остаётся набором обычных значений для **несекретных** переменных. Секреты передаются **по ссылке**: `"envFile": "<путь>"` — путь к файлу env (gitignored), содержимое которого Pegas не читает в манифест, а передаёт Docker через `env_file`. Само значение никогда не попадает ни в манифест, ни в labels, ни в логи Pegas.
- **Обнаружение изменения env-файла**: в label контейнера пишется `pegas.env-hash = <fingerprint>` вычисленный по содержимому файла. Fingerprint не содержит plaintext, но обычный хэш не является криптографической гарантией конфиденциальности: низкоэнтропийные значения могут проверяться перебором. Он не входит в `manifest-hash`; секретные значения не выводятся в логи.
- **Изменение секрета** = изменение `env-hash` при неизменном `manifest-hash`. Контейнер **не перезапускается автоматически**: `pegas dev`/`deploy` сравнивает `env-hash` и сообщает о расхождении так же, как о drift. Пересоздание контейнера (чтобы новые env применились) — через `pegas deploy`, явно.
- Смена `envFile` в контракте (путь) — часть `manifest-hash`: она меняет конфигурацию.

## 5. Семантика команд (новая, при `runtime: "docker"`)

| Команда | Ответственность |
|---|---|
| `pegas init` | Подготовка проекта и создание контракта (как сейчас) |
| `pegas deploy development` | Развёртывание dev-окружения: сеть, gateway, контейнеры, роуты |
| `pegas dev` | Проверка соответствия контракту и подключение к логам; Ctrl+C отваливает логи, не останавливая контейнеры |
| `pegas deploy production` | Развёртывание production-окружения (та же модель) |
| `pegas down` | Остановка ресурсов проекта: контейнеры **удаляются** (не останавливаются); gateway останавливается, когда контейнеров других проектов (включая остановленные) не осталось. `--env <environment>` ограничивает операцию одним окружением checkout |

Сборка: infra-сервисы с готовыми образами — без `--build`; dev-приложения собираются при изменении `build`-полей контракта; исходники не требуют пересборки.

## 6. Миграция и SemVer

Граница стадий S1/S2 (устранение противоречия «Gateway в deploy development, но shared Gateway — в S2»):

- **S1** реализует общий Gateway сразу как shared-ресурс: registry зависимостей через Docker labels (включая остановленные контейнеры) и межпроцессную блокировку для конкурентных `deploy`/`down` входят в базовый runtime. Второй проект не должен конфликтовать с первым, а `down` одного проекта не должен останавливать Gateway, пока существует другой держатель.
- **S2** добавляет эксплуатационное восстановление и hardening: автоматическое восстановление Gateway после аварии при живых контейнерах, CA-доверие для контейнера Gateway и дополнительные recovery-сценарии.

| Стадия | Содержание | Версия |
|---|---|---|
| S1 | Расширение контракта + эфемерный codegen манифеста + labels; opt-in `runtime: "docker"`; Docker runtime для app/infra; общий Gateway, registry зависимостей и безопасная сериализация deploy/down | minor |
| S2 | Восстановление Gateway после аварии при живых контейнерах, CA-доверие для контейнера Gateway и эксплуатационное hardening | minor |
| S3 | Новый `pegas dev` = проверка + attach к логам | minor (внутри opt-in) |
| S4 | Обновление production: новый контейнер → readiness → переключение роута → остановка старого | minor |
| S5 | Смена default → новая модель; deprecated-период старого флоу | **major (2.0)** |

Старый host-флоу (`pegas dev` с локальным Caddy) поддерживается до 2.0 включительно. Инструмент миграции контракта — часть S5.

Registry и координация из 4.1 — обязательная часть S1: временная однопроектная реализация создала бы небезопасную lifecycle-семантику и архитектурный долг.

## 7. Согласованные решения (Q1–Q5, обсуждение 2026-10-31)

### Q1. Dockerfile для dev-приложений — гибридная модель

Принято: Pegas сам обеспечивает типовые dev-образы для распространённых стеков:

- Node.js / Next.js — типовой Node-образ; Bun — типовой Bun-образ; Python — типовой Python-образ.
- Pegas определяет стек, версию runtime и пакетный менеджер по проекту (`package.json`, lock-файл).
- Пользователь может переопределить образ или Dockerfile через `pegas.json` (`image` / `build`).

Принцип: **стандартный проект не требует написания Dockerfile ради работы в Pegas.**

Ограничение: Pegas не пытается угадать любую конфигурацию. Нестандартный проект — пользователь явно описывает параметры в контракте. Если стек не распознан и override не задан — явная ошибка с диагностикой, не тихий fallback на «что-нибудь похожее».

### Q2. Занятые порты 80/443 — fail fast

Принято: никакого автоматического переноса Gateway на 8080/8443 — это ломает обещание локальных доменов без указания порта.

При конфликте Pegas:

- сообщает, какой порт занят (и кем — по возможности);
- показывает вероятную причину;
- не запускает неполноценное окружение и не меняет адреса проекта.

Альтернативные порты в будущем — только через явную конфигурацию в контракте, отдельным режимом, не автоматическим fallback.

### Q3. Синхронизация `node_modules` — named volume + синхронизация по lock-файлу

Модель:

```
Project
  ├── source files → bind mount
  ├── package.json → bind mount
  ├── lock file     → bind mount
  └── node_modules  → named volume
```

- При `deploy development` Pegas проверяет lock-файл (хэш сохраняется в контейнере/volume).
- Изменился — установка зависимостей **внутри контейнера** в существующий volume; не менялся — установка не выполняется.
- Volume **не пересоздаётся** при каждом изменении: сохраняется и синхронизируется по содержимому.

Хост: пользователь ставит зависимости привычным способом (`package.json` + lock-файл через git). Поведение при `npm install` прямо на хосте (появление хостового `node_modules` под bind mount) — см. открытый вопрос Q6.

### Q4. Hot Reload — платформенно-зависимая модель

- Linux: стандартные файловые события (эталон).
- macOS / Windows: штатная синхронизация Docker; polling (CHOKIDAR_USEPOLLING и аналоги) — только там, где требуется, не глобально.
- Поведение переопределяется через `pegas.json`.
- HMR проверяется тестами на поддерживаемых стеках.

Критерий успеха: **Pegas не считает контейнерный dev успешным, если приложение запускается, но изменения файлов не обнаруживаются.** Это главный UX-критерий новой модели.

### Q5. Обновление production-деплоев — целевая модель зафиксирована, реализация вне S1

Целевой механизм обновления (реализация — этап S4 после S1–S3):

1. Собрать новый образ.
2. Запустить новый контейнер.
3. Дождаться успешной проверки готовности.
4. Переключить маршрутизацию на новую версию.
5. Остановить старый контейнер.

Для одного экземпляра приложения без возможности параллельного запуска полноценный zero-downtime deploy **не гарантируется** — это фиксируется в документации честно.

## 8. Критерии готовности S1

Код S1 не начинается, пока не выполнены все пункты:

1. **Контракт v2 спроектирован и покрыт тестами схемы** (все новые поля optional, старые контракты валидны).
2. **Codegen манифеста** эфемерен (D13, D18): безопасный временный каталог с уникальным именем (`pegas-<pid>-<рандом>`), режим 0600, удаление при штатном завершении. Очистка оставшихся временных файлов при следующем запуске — только по маске `pegas-*` своего формата имени **и только при доказанном завершении владельца** (PID + имя процесса + время старта процесса — устойчиво к повторному использованию PID; возраст файла доказательством не является). Секреты в манифест не пишутся. Требуются тесты: **аварийная очистка** — процесс завершается между генерацией и удалением → следующий запуск вычищает остаток; **параллельные процессы** — очистка одного Pegas-процесса не затрагивает временный каталог другого живого процесса (в т. ч. долгоживущего со старым каталогом).
3. **Детекция стека** (Node/Bun/Python, версия runtime, пакетный менеджер) реализована и тестируется на репрезентативных проектах.
4. **Labels** (`pegas.project`, `pegas.service`, `pegas.manifest-hash`) записываются при подъёме и читаются при reconciliation. Требуются **тесты reconciliation**: хэш совпал → изменения отсутствуют; хэш не совпал → drift обнаружен, `pegas deploy` пересоздаёт; контейнеры с разными хэшами → частичный drift диагностируется по сервисам. Семантика `pegas dev` проверяется отдельным этапом S3.
5. **Q2 реализован** (D16): занятость 80/443 проверяется до подъёма gateway; ошибка Docker bind при занятом порту преобразуется в диагностику Pegas (порт, вероятный виновник).
6. **Q3 реализована в базовом виде** (D15): ключ синхронизации = хэш lock-файла + пакетный менеджер + его версия + версия runtime; установка в контейнере выполняется только при изменении ключа, volume сохраняется.
7. **UID/GID-стратегия** (D17) зафиксирована при проектировании типовых образов: пользователь контейнера, права на named volume, поведение при первой установке — спроектированы вместе, с тестом на запись в volume от имени пользователя контейнера.
8. Тесты не зависят от платформы запуска (Linux CI достаточно; платформенные ветки — unit-мок).
9. `pegas.json` без `runtime: "docker"` не меняет поведение ни одной существующей команды.
10. **Shared lifecycle-сценарные тесты** целых потоков: несколько одновременно работающих проектов на общей сети; повторный `deploy` без изменений (идемпотентность); `down` одного проекта не останавливает Gateway при живом соседе; последний `down` останавливает Gateway; `docker stop` контейнера проекта не освобождает зависимость, `docker rm` — освобождает (проверка через `docker ps -a`, а не `network inspect`); конкурентные `deploy`/`down` не приводят к остановке Gateway под подключающимся проектом; аварийно оставшаяся блокировка безопасно восстанавливается или приводит к fail-safe отказу.

> Примечание к покрытию: общий процент покрытия (80% gate) — сигнал качества, но **не** доказательство готовности. Готовность определяется наличием проверок конкретных lifecycle-сценариев: аварийное завершение и повторный запуск, drift, несколько одновременно работающих проектов.
